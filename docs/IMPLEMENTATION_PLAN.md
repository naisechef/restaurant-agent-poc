# Restaurant Agent PoC — Implementation Plan

## Purpose

This document describes the design and implementation plan for a small, professional
proof-of-concept AI agent pipeline that extracts a single structured attribute
(**outdoor seating: yes / no / unknown**) from unstructured restaurant evidence text
using Anthropic's Claude API.

The goal is not to build a production system, but to demonstrate **production-style
engineering judgment** in a compact, testable codebase, organised
explicitly around the concept of **specialised agents operating on a shared, typed
state object**. This mirrors how modern agentic pipelines are structured in
practice — without pulling in an orchestration framework, which would be
unnecessary weight for a system this size.

Core design values:

- Typed, validated data contracts (Pydantic) — the `schemas` for all data flowing
  through the system.
- A single shared `AgentState` object that flows through each pipeline stage,
  rather than ad-hoc variables passed between functions.
- Clear separation of concerns across small, single-responsibility agents:
  preprocessing, extraction, validation.
- Deterministic, pure logic wherever an LLM isn't required — kept fully unit-testable.
- A thin, explicitly-named, mockable LLM boundary (`claude_client.py`), designed so
  a future `openai_client.py` or `gemini_client.py` could sit alongside it without
  touching the rest of the codebase.
- Versioned, isolated prompt content (`prompts/outdoor_seating.py`).
- An evaluation layer plus a **human review queue**, mirroring how a real extraction
  pipeline would route low-confidence predictions in production.
- A CLI entry point, centralised logging, no hardcoded secrets, and no giant script.

## 2. Module Responsibilities

### `config.py`
Centralised configuration and environment loading.

- Loads `.env` (via `python-dotenv`) and reads `ANTHROPIC_API_KEY`.
- Defines a typed `Settings` object (Pydantic `BaseSettings` or a small dataclass)
  holding: model name, max tokens, temperature, request timeout, confidence
  threshold for human review, default input/output paths (including
  `outputs/review_queue.csv`).
- **Fails fast with a clear, actionable error** if `ANTHROPIC_API_KEY` is missing —
  but only when the real Claude client is actually constructed, not at import time,
  so tests and dry runs never require a key.
- No secrets hardcoded; only reads from environment.

### `schemas.py`
Single source of truth for all typed data contracts, using Pydantic. Named
`schemas.py` rather than `models.py` to avoid ambiguity with "ML models" and to
clearly signal these are **data contracts** for API and pipeline I/O.

- `RestaurantRecord`: raw input row (id, name, evidence_text, expected_label — optional).
- `ExtractionResult`: the structured Claude output contract:
  - `label: Literal["yes", "no", "unknown"]`
  - `confidence: float` (0.0–1.0, range-validated)
  - `evidence: list[str]` (short supporting quotes)
  - `reasoning: str`
- Per-record pipeline output is written as row dicts in `pipeline.py` (not a separate
  Pydantic model).
- `EvaluationSummary`: accuracy, precision(yes), recall(yes), false positives,
  false negatives, low-confidence count, total records, failure count.

Schema validation here is intentionally distinct from the business-rule validation
performed later by the Validation Agent — see Design Decisions, item 1.

### `state.py`
Defines `AgentState`: a single Pydantic object that flows through every stage of
the pipeline, replacing the pattern of passing multiple loose variables between
functions. Each agent reads from and returns an updated `AgentState`, which makes
the pipeline easy to trace, log, and test stage-by-stage.

Representative fields:

```python
class AgentState(BaseModel):
    restaurant_id: str
    raw_text: str
    cleaned_text: str | None = None
    prediction: Literal["yes", "no", "unknown"] | None = None
    confidence: float | None = None
    evidence: list[str] = []
    reasoning: str | None = None
    validation_status: Literal["ok", "flagged", "failed"] | None = None
    needs_review: bool = False
    error: str | None = None

Design intent: AgentState is the single object passed between agents —
preprocessing_agent fills cleaned_text, extraction_agent fills
prediction/confidence/evidence/reasoning, validation_agent fills
validation_status/needs_review. This keeps each agent's function signature
identical (AgentState -> AgentState), which is a clean, explainable pattern:
every agent has the same contract — take state in, return state out.
data_loader.py
Responsible only for reading input data and producing validated RestaurantRecord
objects, and seeding the initial AgentState for each row.

load_restaurants(path: Path) -> list[RestaurantRecord]
Uses Pandas (simplicity, ubiquity, easy CSV output later) to read CSV.
Validates/casts each row into RestaurantRecord via Pydantic — invalid rows are
logged and skipped rather than silently ignored or crashing the whole run.
to_initial_state(record: RestaurantRecord) -> AgentState — the seam between raw
input data and the agent pipeline.

prompts/outdoor_seating.py
Isolates all prompt engineering for this specific attribute from application code,
in its own versionable module (a prompts/ package rather than a single file, so
additional attributes — e.g. delivery.py, wheelchair_access.py — could be added
later without touching pipeline code).

Stores the system prompt and a user-prompt template.
build_prompt(evidence: str) -> tuple[str, str] returning (system_prompt, user_prompt).
Plain f-string/.format() templating — no templating engine dependency needed
for a PoC of this size.
Keeping prompts here means prompt tuning is isolated from both the Claude client
and the extraction agent, and prompt content can be reviewed/tested independently.

claude_client.py
Thin wrapper around the Anthropic SDK — the only module that imports
anthropic. Named explicitly (rather than a generic llm_client.py) so that a
future openai_client.py or gemini_client.py could be added side-by-side with
an identical interface, without any generic name colliding or implying a
multi-provider abstraction that doesn't yet exist.

ClaudeClient class (or simple function) with one responsibility: send a
system+user prompt, return raw text response.
Wraps SDK exceptions into a small custom exception (LLMRequestError) so callers
don't need to know about Anthropic-specific exception types.
Configurable via config.Settings (model, max_tokens, temperature, timeout).
This is the seam for mocking in tests — nothing else in the codebase talks to
the network.

logging_config.py
Centralises logging setup so orchestration and agent code stay clean of
boilerplate logging.basicConfig(...) calls.

configure_logging(level: str = "INFO") -> None — sets a consistent formatter
(timestamp, module, level, message) and log level across the app.
Called once, early, from cli.py.
INFO for normal pipeline progress (e.g. "processed record 4/15"), WARNING for
recoverable issues (e.g. a JSON repair retry), ERROR for record-level failures
that get isolated and recorded rather than raised.

agents/preprocessing_agent.py
The first specialised agent in the pipeline. Wraps the pure text-cleaning logic
from preprocessing.py into the AgentState -> AgentState contract.

run(state: AgentState) -> AgentState
Calls preprocessing.clean_evidence(state.raw_text) and populates
state.cleaned_text.
No LLM call, no I/O beyond what's already in state — deterministic and fully
unit-testable via the underlying pure functions.

preprocessing.py
Pure text-cleaning functions — no I/O, no LLM, no side effects. Kept separate
from agents/preprocessing_agent.py so the cleaning logic can be tested in
complete isolation from the agent interface.

normalise_whitespace(text: str) -> str
strip_boilerplate(text: str) -> str (e.g. remove HTML fragments, repeated menu headers)
clean_evidence(text: str) -> str — the composed public function used by the agent.
Deterministic, pure functions → the easiest module to exhaustively unit test.

agents/extraction_agent.py
The core "AI agent" of the pipeline — models the Claude interaction as a
dedicated agent rather than a bare utility function, which better reflects how
agentic systems are structured and is simpler to extend later (e.g. adding an
agent for a second attribute).

run(state: AgentState, client: ClaudeClient) -> AgentState
Calls prompts.outdoor_seating.build_prompt(state.cleaned_text).
Sends the prompt via claude_client, receives raw text.
Parses the response as JSON (guarded try/except), with one repair retry
using a stricter "return valid JSON only" follow-up prompt if the first parse fails.
Validates parsed JSON against ExtractionResult (Pydantic schema validation).
On success: populates state.prediction, state.confidence, state.evidence,
state.reasoning.
On failure: populates state.error and leaves prediction fields None — the
pipeline isolates this as a failed record rather than crashing the batch.

agents/validation_agent.py
Models business-rule validation as its own specialised agent, distinct from
Pydantic schema validation. Although deterministic, giving it an agent interface
keeps the pipeline's mental model consistent: every stage is an agent with the
same AgentState -> AgentState contract, whether or not it happens to call an LLM.

run(state: AgentState, threshold: float) -> AgentState
Checks:

is_confidence_valid — confidence is within expected bounds.
has_supporting_evidence — flags "yes"/"no" predictions with empty evidence
as suspicious.
needs_human_review — confidence below threshold, or evidence missing, or
prior extraction error.


Populates state.validation_status ("ok", "flagged", "failed") and
state.needs_review.
The underlying rule functions live in validation.py as pure functions so they
can be unit-tested without constructing a full AgentState.

validation.py
Pure business-rule validation functions, called by agents/validation_agent.py.

is_confidence_valid(result: ExtractionResult) -> bool
has_supporting_evidence(result: ExtractionResult) -> bool
needs_human_review(result: ExtractionResult, threshold: float) -> bool
No I/O → fully unit-testable without mocking the LLM or constructing AgentState.

evaluation.py
Compares final AgentState predictions to expected labels and produces aggregate
metrics.

evaluate_predictions(states: list[AgentState], expected: dict[str, str]) -> EvaluationSummary
Computes accuracy, precision(yes), recall(yes), false positives, false negatives,
low-confidence case count, and failure count.
Pure functions operating on plain data → easy to test with hand-built fixtures,
no LLM or file I/O involved.

pipeline.py
Orchestration layer — wires the agents together into one end-to-end run over the
shared AgentState. This is the only module that "knows" the full flow; every
other module is a single-responsibility unit.

run_pipeline(input_path, output_path, review_queue_path, settings) -> EvaluationSummary
Flow per record:

Load RestaurantRecord, seed AgentState (data_loader).
agents.preprocessing_agent.run(state).
agents.extraction_agent.run(state, client) — schema validation happens
inside this step via ExtractionResult.
agents.validation_agent.run(state, threshold).
Append to results list; if state.needs_review, also append to the review
queue list.


Per-record failures (LLM errors, malformed JSON after retry) are caught,
recorded on state.error, and excluded from accuracy/precision/recall
denominators but counted explicitly in EvaluationSummary.
After processing all records: calls evaluation.evaluate_predictions, writes
outputs/results.csv (all records) and outputs/review_queue.csv (only
needs_review == True records), and returns the EvaluationSummary.

cli.py
Command-line entry point using argparse (stdlib — no extra dependency needed
for a PoC).

Flags: --input, --output, --review-queue-output (default
outputs/review_queue.csv), --model (optional override), --limit (optional,
for quick smoke runs), --confidence-threshold.
Calls logging_config.configure_logging() first.
Calls pipeline.run_pipeline and prints the EvaluationSummary nicely,
including how many records were routed to the review queue.
Runnable via python -m restaurant_agent.cli --input ... --output ....

tests/

test_preprocessing.py — pure function tests, no mocking needed.
test_validation.py — pure function tests on hand-built ExtractionResult fixtures.
test_evaluation.py — metric correctness tests with a small synthetic labeled
set (including edge cases: all-unknown, empty list, all-correct, all-wrong).
conftest.py — shared fixtures (sample RestaurantRecords, ExtractionResults,
and AgentStates at various stages of completion).
Deliberately no test hits the real Anthropic API — claude_client and the
agents are tested via a fake/mock client where needed (stretch goal, see below).

ARCHITECTURE.md
A short, standalone architecture document (separate from this plan) containing a
single diagram and a paragraph per stage, so a reader can understand the whole
system in under a minute without reading the full implementation plan:

CSV
  ↓
Data Loader
  ↓
AgentState (initialised)
  ↓

4. Design Decisions, Deviations, and Risks
Key design decisions

Two layers of validation are intentional, not redundant.

Schema validation (schemas.py, via Pydantic) — right types, right ranges,
right enum values, enforced the moment Claude's JSON is parsed.
Business-rule validation (validation.py, invoked by
agents/validation_agent.py) — is this confident enough to trust, does it
have evidence, should it be routed to human review.
This separation is intentional: schema validity vs. business trustworthiness
are different concerns and are kept in different modules on purpose.


Every agent shares one interface: AgentState -> AgentState.
This is the main architectural decision in this plan. It means:

Adding a new stage (e.g. a "translation agent" or a second attribute
extractor) requires no changes to the pipeline's shape — just another step
in the same chain.
Every agent can be unit-tested independently by constructing a partial
AgentState and asserting on the returned one.
No orchestration framework is required to get this benefit — a plain
Python function chain over a Pydantic object is sufficient at this scale,
and deliberately avoids introducing LangChain/LangGraph/CrewAI/AutoGen,
which would be disproportionate for a three-agent pipeline.


Error isolation per record. A single malformed Claude response or API
error must not abort the whole batch. pipeline.py wraps each record's
agent chain in a try/except; failures are recorded on state.error with
validation_status = "failed", and are excluded from
accuracy/precision/recall denominators but counted explicitly in
EvaluationSummary — mirroring real-world monitoring practice where
pipeline failures are tracked separately from model disagreement.
"Unknown" handling in metrics. Accuracy is computed over all non-failed
records as exact match (including "unknown" predictions being correct when
the expected label is also "unknown"). Precision/recall for "yes" are
computed in the standard binary sense (yes vs. not-yes), which naturally
folds "unknown" predictions into the "not yes" bucket for false
positive/negative purposes.
Human review queue as a first-class output, not just a metric. Rather
than only reporting a "low-confidence count" in the evaluation summary,
any record where agents/validation_agent.py sets needs_review = True
is written to outputs/review_queue.csv. This is a small addition that
makes the human-in-the-loop story concrete and demoable rather than purely
statistical. Default confidence threshold: 0.6, configurable via CLI/env.
JSON parsing robustness. Claude may occasionally wrap JSON in markdown
fences or add prose. The extraction agent strips common markdown code-fence
patterns before json.loads, and implements exactly one repair retry
with an explicit "output ONLY valid JSON" follow-up prompt before giving up
and marking the record failed. Unbounded retry loops are avoided deliberately
(cost/latency risk).
Mocking strategy for tests. Real API calls must never run in unit tests
(cost, flakiness, secrets in CI). The three core test files are LLM-free by
construction. If agent-level tests are added later, a hand-rolled
FakeClaudeClient (duck-typed to claude_client's interface) is preferred
over a mocking framework — simpler to read and maintain.
Dependency choice: Pandas vs Polars. Given the CSV is tiny, Pandas is the
safer default (ubiquitous, straightforward CSV I/O). Polars is a reasonable
"if I had more time / more data" upgrade, not a requirement here.
Config validation timing. config.py raises a clear, actionable error
(e.g. MissingAPIKeyError) only when ClaudeClient is actually constructed
— not at module import time — so tests and --dry-run mode never require
a key.
No orchestration framework. The AgentState + per-agent
run(state) -> state pattern deliberately does not use LangChain,
LangGraph, CrewAI, or AutoGen. At three agents and one attribute, a
framework would add indirection without adding capability, and would
obscure rather than clarify the design at this scale. This is a conscious
scope decision.
Naming choices matter for clarity. schemas.py (not models.py) and
claude_client.py (not llm_client.py) are chosen specifically to avoid
ambiguity — "models" could be confused with ML models, and a generic LLM
client name could imply a multi-provider abstraction that doesn't exist yet.
Naming things precisely for what they currently do, rather than what they
might become, is itself a design principle worth mentioning.

Risks

LLM output drift: prompt changes or model updates could change
label/confidence behavior; mitigated by strict schema validation in the
extraction agent plus logging of raw responses on failure.
Small sample size: evaluation metrics on ~10–15 rows are illustrative,
not statistically meaningful — stated explicitly in the README.
Cost/secrets in CI: no test or import path may trigger a real API call;
enforced by the mocking strategy above and by deferring API key validation
to client construction time.
Over-modelling determinism as "agents": the validation stage is
deterministic, not LLM-based. This is called out explicitly (see Design
Decision 1) so it doesn't read as inflated terminology — it's framed as
"consistent interface," not "everything is intelligent."
